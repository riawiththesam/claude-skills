# Blind Code Review

## 原則

1. **嘘をつけない情報だけを最初に見せる。** 機械が実行・検証するもの(実装コード、コンパイラが強制する型、設定、スキーマ)が真実の情報源。人間向けの文章(PR本文、commitメッセージ、ブランチ名、コメント、docstring、プランファイル、README、テスト)は「作者の主張」として、あとで検証する対象にする。
2. **コードが基準、文章は検証される側。** Phase 1でコードが実際にやっていることを言語化し、Phase 2でその記述と文章の主張を照合する。
3. **文章は指摘を増やせるが、消せない。** Phase 1の指摘を取り下げてよいのは、コード上の根拠(file:line)が示せるときだけ。「〇〇は作業中なので実装しない」「別PRで対応」と書かれていても、指摘は消さずに観点を変えて残す。

背景: PR説明・commitメッセージ・コメントがLLMレビューに確証バイアスを与え、それらを伏せると見逃しが回復することが報告されている(arXiv:2603.18740)。

## 隔離ルール(Phase 1が終わるまで必ず守る)

- PRのタイトル・本文・commitメッセージ・ブランチ名・PRコメントを読まない。`gh pr view` は前処理スクリプトが `--json` で指定するフィールド以外では実行しない。`gh pr diff`、`git log`、`git show`、`git blame` も実行しない。
- ユーザーの依頼文にPRの説明(「ログイン修正のPR」など)が含まれていても、Phase 1には一切渡さない。Phase 1のプロンプトは下の固定文を使い、置き換えるのはパスだけ。自分の言葉で要約や補足を足さない。
- 前処理は必ずスクリプトで行う。自分でdiffを読んで加工しない。

## Step 0: スクリプトの場所

前処理スクリプトは、このSKILL.mdと同じディレクトリにある `scripts/blind.py`。以降このファイルの絶対パスを `$B` と書く。プロンプトに埋め込むときは絶対パスに展開する。

## Step 1: 前処理

対象リポジトリのルートで実行する。引数($ARGUMENTS)が数字ならPR番号、`--base` で始まればローカルモードとして渡す。引数がなければユーザーに対象を確認する。

```bash
python3 $B prep --pr <PR番号>                     # GitHub PR(gh 必須)
python3 $B prep --base origin/main --head HEAD    # ローカルのブランチ差分
```

1行目に出力ディレクトリ(以降 `$DIR`)が表示される。中身は次のとおり。

- `diff.txt`: コメントを除去した差分。テスト・ドキュメント・プランファイル・ロックファイルは除外済みで、件数だけが記載される。行番号は実ファイルと一致する。
- `head/`: 変更ファイルの、変更後の全文(コメント除去済み)
- `manifest.json`: head/baseのSHAと、ファイルの分類

## Step 2: Phase 1(ブラインド評価)

Agentツールで、新しいサブエージェント(subagent_type: general-purpose)を起動する。プロンプトは次の固定文とし、`{DIR}` と `{B}` だけを絶対パスに置き換える。

```text
あなたはコードレビュアーです。作者による説明は一切与えられません。コードだけを根拠に判断してください。

入力:
- {DIR}/diff.txt : 変更差分。コメントは除去済みで、テストとドキュメントは除外済み。列は「旧行番号 新行番号 記号| コード」で、行番号は実ファイルと一致する。
- {DIR}/head/ : 変更ファイルの変更後の全文(コメント除去済み)
- 変更されていないファイルを見たいとき:
  - python3 {B} show --dir {DIR} <path>     ファイルを表示する
  - python3 {B} ls --dir {DIR} [<dir>]      ファイル一覧を表示する
  - python3 {B} grep --dir {DIR} <文字列>   固定文字列で検索する

禁止事項:
- 上記以外の方法でリポジトリを読むこと(リポジトリに対して直接 Read / cat / grep を使う、git log / show / blame、gh コマンド、テストファイル・Markdown・ドキュメントを開く)。
- 作者の意図を推測で補って、問題を「たぶん意図的」と見逃すこと。

観点:
- 名前を信用しない: 関数名・変数名・型名が示す振る舞いと、実際の振る舞いが一致しているかを確かめる。
- 強制されない型を信用しない: TypeScript の any / as / 非nullアサーション(!)、Kotlin の !! や unchecked cast があれば、型による保証はないものとして扱う。
- 「呼び出し元が保証しているはず」で済ませず、必要なら show / grep で呼び出し元・呼び出し先を確認する。
- 未完成に見える箇所(空実装、TODO()、固定値を返すだけの実装、到達可能なのに中身のない分岐、握りつぶされた例外)は必ず挙げる。
- diff.txt に WARNING 付きのファイルがあれば、その中のコメントは検証されていない主張として扱う。

出力: {DIR}/phase1.md に次の形式で書き、最後に同じ内容を返答する。

## A. このdiffが実際にやっていること
振る舞い、副作用(I/O・DB・ネットワーク・状態の変更)、外部インターフェースの変更を、事実として列挙する。各項目に file:line を付ける。

## B. 推測される目的
コードから読み取れる目的を、確信度(高/中/低)と根拠つきで書く。目的が読み取れない箇所は「意図不明」として挙げる。

## C. 扱っていない入力・ケース

## D. 未完成に見える箇所
各項目について、マージ後にその箇所へ到達可能かどうかも書く。

## E. 指摘
各指摘を次の形式で書く: [critical/major/minor] file:line — 内容 — 根拠 — どういう入力・状態で壊れるか
```

サブエージェントが終わったら `$DIR/phase1.md` を読む。**ここまで来たら、初めて文章側を読んでよい。**

## Step 3: Phase 2(文章の照合)

自分で行う。文章側の情報を集める。

```bash
gh pr view <N> --json title,body,commits,comments,reviews
gh api repos/{owner}/{repo}/pulls/<N>/comments     # インラインのレビューコメント
gh pr diff <N>                                      # 生のdiff(コメント・テスト・プランファイルを含む)
```

ローカルモードの場合は、`git log <base>..<head>` と `git diff <base>...<head>` を使う。

次の場所から「主張」を1つずつ抜き出す。

- PRのタイトル・本文・commitメッセージ:「〇〇を修正」「△△には影響しない」「□□は未実装」など
- 追加・変更されたコード内のコメントとdocstring:「nullにならない」「スレッドセーフ」「呼び出し元で検証済み」など
- プランファイルやドキュメント: 計画された項目と、実装済みとされている項目
- テスト: テスト名や説明が主張している振る舞い。テストが実際にそれを検証しているか

各主張を、`phase1.md` と実コード(必要なら `git show <head>:<path>`)に照らして判定する。

- ✅ 一致: Phase 1の記述やコードと合っている
- ❌ 矛盾: コードと食い違っている(嘘、古い記述、実装漏れ)
- ❓ 確認不能: コードからは判断できない

### 特に注意する主張

- **スコープ除外(「作業中」「別PRで対応」「今回は実装しない」):** 関連するPhase 1の指摘は消さない。代わりに次の点を確認する。
  - その未実装部分は、マージ後に到達可能か(フィーチャーフラグや入口の封鎖で守られているか)
  - 中途半端な状態でマージされても安全か(データ不整合、例外、セキュリティ上の穴が出ないか)
  - 「実装しない」と書いてあるのに、実際には一部だけ実装されていないか
- **安全性の主張(「影響なし」「後方互換」「検証済み」):** Phase 1のA(副作用・インターフェース変更)と突き合わせる。
- **テスト:** Phase 1のC(扱っていないケース)のうち、どのテストでも検証されていないものを挙げる。

## Step 4: 統合する

- Phase 1の各指摘は、次のいずれかとして扱う。
  - **維持する**
  - **取り下げる**: コード上の根拠(file:line)を必ず書く。文章で説明されていることは、取り下げの理由にならない。
  - **維持して注記する**: 文章で「意図的」とされている場合。「意図的とされているが、〜の状態では〜が起きる」と書く。
- Phase 2で見つかった不一致(❌)は、新しい指摘として加える。
- Phase 1で「意図不明」だった箇所のうち、文章を読んで初めて理解できたものは、可読性の指摘(命名や構造で意図を表せていない)として残す。

## 出力フォーマット

ユーザーへの最終報告は次の構成にする。PRへの投稿は、ユーザーに頼まれたときだけ行う(`gh pr review <N> --comment --body-file <file>`)。

```markdown
## 1. コードが実際にやっていること
(Phase 1のAとBの要約)

## 2. 指摘(重要度順)
- [major] path:line — 内容 — 出典: Blind / 照合 — 状態: 維持 / 注記つき

## 3. 文章とコードの照合
| 主張 | 出典 | 判定 | 根拠 |
|---|---|---|---|

## 4. スコープ外・未実装とされた部分
(到達可能か、マージしても安全か)

## 5. 取り下げた指摘
(コード上の根拠つき)
```

## 限界

- サブエージェントの隔離は、プロンプトでの指示による約束であり、技術的に強制されているわけではない。
- 識別子名とファイルパスは残る。そのため、Phase 1の観点に「名前を信用しない」を入れている。
- TypeScriptのJSXテキスト内にある `//` と、正規表現リテラルの判定はヒューリスティック。YAMLなど `#` コメントの言語は、行全体がコメントの行だけを除去する。
- 対応していない拡張子のファイルは、コメントを除去せずに含め、diff.txtで WARNING を付ける。
